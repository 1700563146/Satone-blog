## 1. 文档目的

本文档用于指导从零开发一个可长期维护的个人博客系统，覆盖产品范围、参考项目分析、技术选型、系统架构、目录设计、数据模型、开发阶段、测试、部署、安全和验收标准。

本文不是对参考项目源码的逐文件审计。当前分析依据其公开仓库页面与 README
中可见的项目介绍、目录划分、部署流程及功能说明；在真正编码前，仍应克隆仓库并核查具体实现、依赖版本、许可证全文和关键代码。

## 2. 项目目标与边界

### 2.1 项目目标

-   建立个人品牌展示与文章发布的统一入口。
-   提供清晰、舒适、具有辨识度的阅读体验。
-   支持以 Markdown 为核心的写作工作流。
-   将文章、标签、分类、站点配置和媒体资源组织成可维护的数据。
-   支持可靠部署、备份、恢复和持续迭代。
-   为未来的评论、搜索增强、统计、友链等能力预留扩展点。

### 2.2 首期非目标

为避免首版过度复杂，以下功能暂不作为 MVP 的硬性要求：

-   多用户、角色权限和复杂团队协作。
-   自建通用 CMS 或复杂可视化页面搭建器。
-   自建图片存储服务。
-   AI 聊天助手、等级体系、创意工坊或复杂社区。
-   复杂数据分析平台和实时推送系统。

### 2.3 设计原则

1.  **内容优先**：文章内容与网站主题、组件实现分离。
2.  **先简单后扩展**：单体应用优先，不因未来可能的需求提前拆微服务。
3.  **可迁移**：文章采用 Markdown/MDX
    等可移植格式，避免锁死在某个专有平台。
4.  **安全默认**：管理功能不公开暴露；密钥不进入客户端和 Git。
5.  **可验证**：每个阶段有可执行的验收标准。
6.  **渐进增强**：先保证核心阅读与写作体验，再加入装饰和高级交互。

### 3.3 不建议直接照搬的部分

-   **不要默认复制整个项目结构。**
    原项目的本地管理器和同步流程服务于它自己的发布模式；你的项目应根据实际写作习惯选择管理方案。
-   **不要首版堆叠全部功能。** AI
    助手、音乐、评论、动态、等级系统会增加配置、维护和安全成本。
-   **不要让内容发布依赖手工复制多个目录。**
    应明确内容的唯一来源，尽可能由构建流程自动完成。
-   **不要把毛玻璃当作全部设计。**
    它应是视觉语言之一，而不是牺牲阅读性、加载速度和移动端体验的理由。
-   **不要未经审查复制代码或素材。** 许可证为 CC BY-NC
    4.0；非商业许可不等于可以无条件用于任何用途。需要特别确认署名、衍生作品及商业限制。

## 4. 产品规划

### 4.1 用户与使用场景

首期以单一站长为内容维护者，普通访客为阅读者。

-   访客：浏览首页、查看文章、按标签筛选、搜索、访问关于页面。
-   站长：创建文章、编辑草稿、预览内容、发布或取消发布、上传图片、维护站点资料。
-   维护者（通常也是站长）：配置站点、查看构建结果、备份与恢复内容。

### 4.2 功能分级

#### P0：MVP 必须完成

-   首页与文章列表。
-   文章详情页。
-   Markdown 内容渲染、代码高亮、目录。
-   分类与标签。
-   关于页面与基本导航。
-   响应式布局。
-   SEO 基础：标题、描述、规范 URL、Open Graph、sitemap、robots。
-   404 页面与基础错误处理。
-   内容版本控制与部署流程。
-   基础测试、格式检查、构建检查。

#### P1：首版稳定后增加

-   后台文章管理。
-   草稿、预览、发布状态。
-   站内搜索。
-   RSS Feed。
-   友链页面。
-   深色/浅色主题。
-   图床或对象存储上传。
-   访问统计。
-   评论系统（优先考虑第三方托管方案）。

#### P2：按真实需求决定

-   定时发布。
-   全文搜索引擎。
-   文章系列与阅读进度。
-   音乐播放器。
-   AI 写作辅助或问答。
-   多语言。
-   复杂内容工作流、多个作者、角色权限。

### 4.3 主要页面

  ---------------------------------------------------------------------------------------------
  路由                    页面用途                关键内容
  ----------------------- ----------------------- ---------------------------------------------
  `/`                     首页                    个人简介、精选文章、最新文章、分类入口

  `/posts`                文章列表                分页、标签、分类、搜索入口

  `/posts/[slug]`         文章详情                标题、摘要、日期、正文、目录、上一篇/下一篇

  `/categories/[slug]`    分类归档                分类介绍、文章列表

  `/tags/[slug]`          标签归档                标签信息、文章列表

  `/about`                关于                    个人介绍、技能、项目与联系方式

  `/friends`              友链                    友链列表（可放到 P1）

  `/search`               搜索                    查询、结果、空状态

  `/admin`                管理后台                仪表盘、文章管理、设置（启用后台时）
  ---------------------------------------------------------------------------------------------

### 5.2 为什么推荐 Markdown 优先

个人博客的主要资产是文章，而不是后台程序。将文章存为 Markdown 能带来：

-   文章和代码一起进行版本控制。
-   可以离线写作和备份。
-   不依赖某个 CMS 才能读取内容。
-   方便迁移到其他博客框架。
-   便于通过 Git 记录修改历史。

但纯 Markdown
文件方案也有代价：在网页后台编辑文件、并发修改、草稿预览、上传图片、定时发布等功能，需要额外设计。若你明确需要完整网页后台，应在项目早期决定采用数据库内容模型，或采用"后台写入内容文件并触发构建"的模式。

### 5.3 两种内容架构

#### 方案 A：静态内容优先（建议先做）

-   文章保存在 `content/posts/*.md`。
-   构建时读取文章并生成页面。
-   Git 是文章版本历史与备份的重要组成部分。
-   初期可不提供在线管理后台，先使用本地编辑器。
-   如需后台，可在后续通过受保护的写入 API 或独立管理工具接入。

适合：个人博客、低维护成本、重视内容可迁移性。

#### 方案 B：数据库 + 在线管理后台

-   文章、标签、分类、站点设置保存在数据库。
-   后台提供登录、编辑、预览、发布等操作。
-   图片保存到对象存储或图床。
-   发布后通过缓存失效或重新生成页面更新前台。

适合：希望完全通过浏览器管理、需要定时发布或动态配置的站长。

**决策建议：** 如果你还没有明确要求"任何设备都能在线写作"，首期采用方案
A。先完成前台与内容流程，再决定是否迁移到方案
B。不要在没有实际需求时同时维护文件和数据库两套真相来源。

## 6. 系统架构

### 6.1 推荐的 MVP 架构

``` text
访客浏览器
    |
    v
Next.js 页面层
    |-- 首页 / 列表 / 详情 / 归档 / 关于
    |-- SEO 元数据 / sitemap / RSS
    |
    v
内容访问层
    |-- 读取 Markdown
    |-- 校验 frontmatter
    |-- 解析正文
    |-- 生成目录与代码高亮
    |
    v
content/posts + content/pages
    |
    v
Git 仓库 -> CI 检查与构建 -> 部署平台
```

### 6.2 后台阶段架构

``` text
站长浏览器
    |
    v
/admin 页面
    |
    v
服务端鉴权与授权
    |
    v
业务服务层
    |-- 文章管理
    |-- 分类/标签
    |-- 媒体上传
    |-- 站点设置
    |
    +--> PostgreSQL（若采用数据库方案）
    |
    +--> 对象存储/图床（媒体文件）
    |
    v
缓存失效 / 页面重新生成 / 部署发布
```

### 6.3 架构边界

-   页面组件负责展示与交互，不直接散落地访问数据源。
-   内容读取与校验集中在 `lib/content`。
-   业务规则集中在 `lib` 或 `services`，避免重复写在页面中。
-   第三方服务封装在 `lib/integrations`，便于更换服务商。
-   管理端写操作必须在服务端完成鉴权、校验和授权。
-   只有公开内容可以被前台读取；草稿与后台配置不得进入公开数据接口。
-   MVP 不需要微服务、消息队列或 Kubernetes。

## 8. 内容模型与 Markdown 规范

### 8.1 文章 Frontmatter

``` yaml
---
title: "我的第一篇文章"
slug: "first-post"
description: "文章摘要，用于列表和搜索引擎摘要"
date: "2026-10-23"
updatedAt: "2026-10-23"
published: true
draft: false
categories:
  - "开发记录"
tags:
  - "博客"
  - "Next.js"
cover: "/images/posts/first-post.webp"
featured: false
---
```

字段说明：

  字段            类型          规则
  --------------- ------------- --------------------------------------------
  `title`         string        必填
  `slug`          string        必填、唯一、稳定；发布后变更需处理重定向
  `description`   string        建议必填，用于列表摘要和 SEO
  `date`          date/string   必填，明确时区策略
  `updatedAt`     date/string   可选
  `published`     boolean       是否对外发布
  `draft`         boolean       草稿标志；与 `published` 的规则需统一
  `categories`    string\[\]    可选
  `tags`          string\[\]    可选
  `cover`         string        可选，必须是合法的本地路径或允许的媒体 URL
  `featured`      boolean       可选

### 8.2 发布规则

-   公开构建只能收录明确允许发布的文章。
-   `draft: true` 或 `published: false`
    的文章不得出现在列表、搜索、RSS、sitemap 或公开 API。
-   `slug` 必须唯一；构建阶段发现重复时应直接失败。
-   日期使用 ISO 格式；展示时采用站点配置指定的时区。
-   正文 Markdown 应对危险 HTML 做安全处理。
-   外链默认采用安全属性；外部图片的加载策略应可配置。
-   图片要有替代文本，代码块需保留语言标识。

### 8.3 迁移到数据库时的逻辑实体

-   `Post`：文章主体、slug、摘要、正文、状态、发布时间。
-   `Category`：分类。
-   `Tag`：标签。
-   `PostTag`：文章与标签的多对多关系。
-   `SiteSetting`：站点名称、简介、主题、社交链接等。
-   `MediaAsset`：文件地址、类型、尺寸、替代文本、上传时间。
-   `User` / `Session`：只有启用后台认证时才需要。

不要为了"以后可能需要"而提前建立大量无用表。数据库模型应跟随已确认的功能需求演进。

------------------------------------------------------------------------

## 9. UI 与视觉规范

### 9.1 设计方向

可以借鉴参考项目的毛玻璃风格，但建议形成自己的视觉标识：

-   低饱和度背景与明确的文字层级。
-   半透明卡片只用于导航、摘要、浮层等适当位置。
-   标题、正文、元信息使用稳定的字号和行高体系。
-   动画短而克制，不影响滚动和阅读。
-   图片封面保持统一比例，避免列表布局跳动。
-   移动端减少模糊层、阴影和大面积固定背景，优先保证流畅度。

### 9.2 设计 Token

建议通过 CSS 变量集中管理：

``` css
:root {
  --color-bg: #f5f6f8;
  --color-surface: rgba(255, 255, 255, 0.72);
  --color-text: #20242c;
  --color-muted: #687080;
  --color-border: rgba(30, 40, 60, 0.12);
  --color-accent: #6478d3;

  --radius-card: 18px;
  --radius-control: 10px;
  --content-width: 760px;
  --page-width: 1120px;

  --shadow-card: 0 8px 28px rgba(25, 35, 55, 0.08);
}
```

上述值是初始参考值，后续应根据真实页面和对比度检查调整。不要在每个组件中单独写一套颜色和圆角。

### 9.3 响应式要求

-   从小屏幕开始设计，至少检查窄手机、普通手机、平板和桌面布局。
-   导航栏在小屏幕下应有清楚的折叠方案。
-   正文不能横向溢出；代码块应在容器内横向滚动。
-   可点击目标应有足够尺寸，键盘焦点必须可见。
-   尊重 `prefers-reduced-motion`，避免强制播放大幅动画。
-   确保毛玻璃背景上的文字对比度符合可访问性要求。

## 10. 搜索、SEO 与性能

### 10.1 SEO 首期要求

-   每个页面都有唯一的标题和描述。
-   文章 URL 稳定且可读。
-   生成 sitemap 与 robots 文件。
-   文章页配置规范 URL（canonical）和 Open Graph 元信息。
-   站点图标、社交分享图和站点名称统一。
-   对文章列表、标签页、分页设置合理的索引策略。
-   不把草稿、管理页或内部 API 放入 sitemap。
-   RSS 仅输出公开发布的文章。

### 10.2 性能要求

-   优先使用服务端组件，只有需要交互时才使用客户端组件。
-   图片按需优化，配置明确的尺寸与替代文本。
-   避免将整篇文章内容重复打包进不必要的客户端 JavaScript。
-   动画避免持续消耗 GPU；谨慎使用全屏 `backdrop-filter`。
-   对字体、图片和第三方脚本进行体积控制。
-   在发布前记录构建结果，并用 Lighthouse 或同类工具检查主要页面。

### 10.3 搜索实现路径

MVP
可先使用构建时生成的文章索引，在客户端进行标题、摘要、标签匹配。文章量明显增长后，再考虑专用全文检索。不要在没有规模需求时先引入独立搜索服务。

------------------------------------------------------------------------

## 11. 安全、隐私与可靠性

-   后台不得只依赖前端隐藏菜单；所有写操作都必须在服务端验证身份和权限。
-   密码使用成熟认证方案与安全哈希算法，禁止明文保存。
-   API Token、数据库密码、OAuth Secret 必须放入环境变量或托管密钥系统。
-   `.env*`、备份文件、私密配置不得提交到公开仓库；提交 `.env.example`
    时只写占位符。
-   上传接口需校验文件类型、大小、扩展名和目标存储权限。
-   对 Markdown/MDX 的原始 HTML
    和动态组件实施安全策略；不要执行不可信文章中的任意代码。
-   管理 API 根据风险配置速率限制、CSRF 防护、输入验证和日志。
-   生产环境避免输出密钥、会话令牌、用户隐私或完整异常堆栈。
-   定期备份文章、数据库和媒体索引；备份方案必须配套恢复演练。
-   对外部评论、音乐、统计等第三方脚本进行隐私与加载性能评估。

------------------------------------------------------------------------

## 12. 开发路线与里程碑

推荐以可交付成果推进，而不是一次性实现所有页面。

### 阶段 0：需求与仓库审查

任务： - 阅读参考项目 README、许可证和更新日志。 -
如需深入借鉴，克隆仓库并检查关键源码与依赖。 -
确定博客定位、视觉方向、是否需要在线后台、部署平台和预算。 - 将 P0/P1/P2
功能写入任务看板。

交付物： - `docs/PRODUCT_SCOPE.md` - `docs/ARCHITECTURE.md` -
`docs/DECISIONS.md`

验收： - 首期功能范围明确。 - 内容存储方案和部署方案已确定。 -
参考代码/素材的许可证使用边界已核对。

### 阶段 1：项目骨架

任务： - 初始化 Next.js + TypeScript 项目。 - 配置 Tailwind
CSS、代码规范、格式化和测试。 - 建立目录结构、全局布局、基础导航和设计
Token。 - 配置 CI：安装、lint、类型检查、测试、构建。

交付物： - 可本地运行的空博客。 - `README.md` 和 `.env.example`。 -
自动化检查流程。

验收： - 新环境按文档可安装并运行。 - CI
对错误的类型、格式和构建问题能失败退出。

### 阶段 2：内容引擎

任务： - 定义文章 frontmatter schema。 - 实现 Markdown
文件读取、解析、排序、标签分类提取。 - 实现草稿过滤、slug
唯一性校验、目录生成。 - 添加示例文章和内容校验脚本。

交付物： - `lib/content`。 - 内容规范文档。 - 内容单元测试。

验收： - 非法 frontmatter 或重复 slug 能在构建时被发现。 -
草稿不出现在任何公开列表或元数据中。

### 阶段 3：前台页面

任务： - 完成首页、文章列表、文章详情、分类、标签、关于页面。 -
完成代码高亮、目录、上一篇/下一篇。 - 实现空状态、404、移动端导航。 -
完成基础 SEO、RSS、sitemap。

交付物： - 功能完整的博客前台。 - 响应式页面与组件。

验收： - 主要路由无错误。 - 手机和桌面都可正常阅读。 -
键盘导航、图片替代文本和正文对比度通过基本检查。

### 阶段 4：部署与可观测性

任务： - 创建部署项目并配置环境变量。 - 连接 Git 仓库和自动部署。 -
配置自定义域名、HTTPS 与 DNS。 - 设置错误监控或最基本的部署日志检查。 -
记录回滚与恢复步骤。

交付物： - 可公开访问的网站。 - `docs/DEPLOYMENT.md`。 -
备份与回滚说明。

验收： - 主分支提交可以自动触发检查和部署。 - 部署失败可定位原因。 -
旧版本能够回滚。

### 阶段 5：写作体验与增强功能

按优先级选择： - 后台登录与文章管理。 - 图床上传。 -
搜索、友链、评论、主题切换。 - 定时发布、统计、AI 等高级功能。

验收： - 每个功能有明确的权限、错误状态、测试与关闭方式。 -
新功能不破坏已有文章 URL、SEO 和移动端体验。

## 13. 测试与验收策略

### 13.1 单元测试

覆盖： - frontmatter 解析与校验。 - slug 生成和重复检测。 - 草稿过滤。 -
日期排序与时区展示。 - 标签、分类聚合。 - Markdown 处理中的安全规则。

### 13.2 集成测试

覆盖： - 文章列表只返回公开文章。 - 文章详情可按 slug 找到内容。 - 无效
slug 返回 404。 - sitemap、RSS 不包含草稿。 -
图片路径和外部链接按规则处理。

### 13.3 端到端测试

至少覆盖： - 首页打开并进入一篇文章。 - 通过标签进入归档页。 -
搜索得到结果和空结果。 - 移动端菜单可打开、关闭和导航。 -
若存在后台：未登录写操作被拒绝；登录后可创建草稿、预览、发布和撤回。

### 13.4 发布门槛

每次合并到主分支前至少执行：

``` bash
npm run lint
npm run typecheck
npm run test
npm run build
```

只有在 `package.json`
已定义对应脚本后，才可使用这些命令；若使用其他包管理器，统一改用对应命令。不得通过删除检查或忽略错误来让构建"变绿"。

## 14. 部署与运维

### 14.1 推荐发布流程

``` text
本地开发
  -> 代码格式与类型检查
  -> 单元/集成测试
  -> Pull Request 或提交检查
  -> CI 构建
  -> 预览部署
  -> 验收
  -> 生产部署
  -> 冒烟测试
```

### 14.2 环境区分

-   `development`：本地开发数据与本地环境变量。
-   `preview`：测试部署，不使用生产密钥或生产写入权限。
-   `production`：正式网站，密钥最小权限，限制管理入口。

### 14.3 备份策略

Markdown 方案： - Git 远程仓库作为一层版本备份。 -
定期导出文章、图片清单和站点配置。 -
媒体文件若托管在第三方服务，应保存清单并确认可批量导出。

数据库方案： - 自动数据库备份。 - 媒体对象存储单独备份或启用版本控制。 -
定期验证恢复步骤，而不是只确认备份任务"成功"。

## 16. 开发约束与团队规范

即使项目只有一个开发者，也建议执行以下约束：

1.  所有新功能先明确用户场景、验收条件和影响范围。
2.  先完成可工作的最小实现，再做动画和装饰细节。
3.  页面不直接重复实现内容读取逻辑。
4.  公共文章必须经过统一的内容校验和发布过滤。
5.  不提交密钥、个人访问令牌、数据库转储或私密草稿。
6.  新增依赖前说明用途；优先采用成熟且仍维护的依赖。
7.  任何架构变更记录在 `docs/DECISIONS.md`。
8.  每个阶段完成后运行 lint、类型检查、测试与生产构建。
9.  数据结构变化必须考虑已有文章和 URL 的兼容性。
10. 删除、覆盖文章或迁移数据前先备份。
11. 不以未经验证的截图、示例数据或模拟接口冒充已实现功能。
12. UI 组件要支持加载、成功、失败、空数据和窄屏状态。
13. 外部服务不可用时，核心文章阅读应尽量仍然可用。
14. 所有关键操作提供可理解的错误信息，不向访客暴露内部堆栈。

### 16.1 Git 分支与提交

个人项目可以采用简单流程：

-   `main`：始终保持可构建、可部署。
-   `feat/<name>`：功能开发分支。
-   `fix/<name>`：问题修复分支。
-   提交信息建议使用 `feat:`、`fix:`、`docs:`、`refactor:`、`test:`
    等前缀。

## 18. Definition of Done（完成定义）

一个功能只有同时满足以下条件才算完成：

-   [ ] 功能与验收标准一致。
-   [ ] 主要成功、失败、空状态已实现。
-   [ ] TypeScript、lint 和相关测试通过。
-   [ ] 不存在明显的桌面或移动端布局问题。
-   [ ] 无密钥泄漏和明显权限绕过。
-   [ ] 相关文档与配置示例已更新。
-   [ ] 对现有 URL、内容和 SEO 的影响已评估。
-   [ ] 在预览环境完成验证。
-   [ ] 如涉及数据修改，已明确备份与回滚方式。

## 19. 建议的第一周执行顺序

1.  克隆并审查参考仓库，核对许可证和功能实现边界。
2.  确认是否需要网页后台，以及是否接受 Markdown 文件作为主要内容源。
3.  创建自己的 Git 仓库和 Next.js 项目。
4.  配置 TypeScript、lint、格式化、测试和 CI。
5.  实现文章 frontmatter schema、内容读取与草稿过滤。
6.  完成首页、文章列表和文章详情三个核心页面。
7.  加入移动端布局、404、SEO、sitemap 和 RSS。
8.  部署预览版，验证文章发布和回滚流程。
9.  根据实际使用体验再决定后台、图床、搜索与评论的优先级。

------------------------------------------------------------------------

## 20. 最终建议

最稳妥的路线不是复制一整套复杂博客平台，而是分三步：

1.  **先做内容可靠的博客前台**：页面、Markdown、分类标签、SEO、响应式和部署。
2.  **再完善写作与管理**：预览、草稿、图片上传、后台鉴权与发布工作流。
3.  **最后增加特色体验**：毛玻璃视觉深化、主题、评论、音乐、AI
    或其他个人化功能。

这样可以尽早得到一个真正可用的个人博客，同时保留后续演进空间。最重要的架构决定是：**明确内容的唯一真实来源，并让发布、备份和恢复围绕它设计。**
